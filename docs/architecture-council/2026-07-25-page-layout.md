# Независимый лист и рамки компоновки

Дата: 2026-07-25  
Статус: Accepted

## Контекст

Исторически размер `PaintWidget` одновременно является размером итогового
листа и входом для компоновки задачи. Общая текстовая подпись резервирует
нижнюю часть листа через вычисляемые `hcenter` и `text_height`, а несколько
пространственных задач включают подпись в собственную Scene и изменяют размер
canvas после рендера.

Пользователю нужны независимо изменяемый лист и две редактируемые области:
задача и текстовая подпись. При этом изображение, открытое со старым JSON- или
pickle-sidecar, до изменения компоновки должно воспроизводиться в прежнем
виде.

## Принятое решение

Ввести опциональный версионированный `page_layout` со следующими правилами:

1. Существующий `canvas.width/height` остаётся размером листа.
2. `page_layout` хранит независимые пиксельные `task_frame` и `note_frame`:
   `x`, `y`, `width`, `height`.
3. Отсутствующий `page_layout` означает legacy render mode. Старый документ
   использует прежний путь компоновки без автоматического преобразования и
   сохраняет raster baseline.
4. Для hover старого документа рамки могут быть вычислены временно, но
   `page_layout` материализуется только при первом перемещении или изменении
   размера рамки.
5. Изменение размера `task_frame` передаёт layout builder новые доступные
   ширину и высоту и запускает перекомпоновку. Готовая Scene или растровое
   изображение не масштабируется.
6. `note_frame` задаёт независимую область компоновки общего текста.
7. Рамки, grip и resize handles являются editor overlay и не входят в экспорт.
8. Внутренность `task_frame` сохраняет предметный hit-testing. Перемещение
   рамки выполняется только за отдельный grip; стороны и углы изменяют размер.
9. Приоритет событий: resize handle, затем grip, затем предметное
   взаимодействие задачи.

Планируемое представление:

```json
{
  "canvas": {"width": 800, "height": 600},
  "extensions": {
    "page_layout": {
      "version": 1,
      "task_frame": {"x": 30, "y": 20, "width": 740, "height": 430},
      "note_frame": {"x": 40, "y": 470, "width": 720, "height": 100}
    }
  }
}
```

## Обоснование

- Опциональное расширение позволяет старым документам открываться без
  миграционного изменения координат и округлений.
- Перекомпоновка сохраняет размеры шрифтов, стрелок, линий, шарниров и других
  условных обозначений; геометрическое масштабирование исказило бы чертёж.
- Grip не отнимает внутреннюю область задачи у draggable labels, контекстных
  меню и интерактивного построения стержней.
- Пиксельные координаты соответствуют принятому Scene-контракту и позволяют
  проверять переход raster baseline.

## Рассмотренные альтернативы

### Немедленная миграция всех старых документов

Отвергнута: даже математически эквивалентные рамки могут изменить измерение
текста, округление координат и viewport отдельных задач.

### Масштабирование готовой Scene

Отвергнуто: меняет толщины линий, размеры текста и инженерных обозначений либо
требует сложного гибридного масштабирования.

### Старое изображение как неизменяемая подложка

Отвергнуто: гарантирует первый кадр, но разрывает связь с редактируемой
предметной моделью и не даёт корректного поведения после изменений задачи.

### Перемещение за любую точку внутри рамки

Отвергнуто из-за конфликтов с перетаскиваемыми подписями, узлами, контекстными
меню и построением геометрии.

## Последствия и риски

- До завершения миграции всех задач временно сосуществуют legacy и framed
  render modes.
- Три auto-size типа (`stress-cube`, `shafts-pipes`, `spatial-beams`) должны
  отделить note layout и научиться принимать доступный размер task frame.
- Преобразование координат событий обязано учитывать начало task frame.
- Минимальные размеры рамок и политика выхода за границы листа должны быть
  единообразны; рекомендуемое первое правило — рамка целиком ограничена листом.
- Старый документ перестаёт требовать побитового совпадения только после
  явного изменения его компоновки пользователем.
